# 测试与质量保障（M4）

> 本文档说明 `planewar` 的测试策略与内存安全保障。重点不是「测试覆盖多少」，
> 而是**用最小代价把「架构纪律」变成可验证的事实**——这对面试讲「工程质量」很有用。

---

## 1. 单元测试：零依赖、脱离 SFML

### 1.1 为什么自己写 harness 而不是用 Catch2

Catch2 / GoogleTest 是更好的选择，但本项目是**入门 demo**，引入它们需要：
- 网络拉取（或 vendored 单头文件），增加构建不确定性；
- 对「只有 Java/Python 基础」的读者增加认知负担。

所以这里用一个 **~50 行的注册表式 harness**（`tests/test_framework.h` +
`tests/test_main.cpp`）。它支持 `TEST()` / `EXPECT_TRUE` / `EXPECT_FALSE` /
`EXPECT_EQ` / `EXPECT_FLOAT_EQ`，足以表达本项目纯逻辑单元的断言。

> 面试话术：「我评估过 Catch2，但判定它对入门 demo 是 over-engineering；
> 一个 50 行的 harness 既能证明我会写测试，又不给构建加负担。规模上来后我会换 Catch2。」

### 1.2 能测什么、不能测什么（诚实边界）

测试目标 `PlaneWarTests` **只编译 SFML-free 的纯逻辑头文件**，不链接 SFML、也不编译游戏 `main`/实体 `.cpp`：

| 被测单元 | 文件 | 类型 | 验证点 |
|---|---|---|---|
| `Vec2` 向量 | `core/Math.h` | 头文件 | 加减乘、长度、距离平方 |
| 对象池 | `game/ObjectPool.h` | 头文件(模板) | Acquire/Release、池满返回 null、槽位复用、ForEachActive |
| 事件总线 | `game/events/EventBus.h` | 头文件 | 类型安全分发、多订阅者、无订阅者静默、Clear |
| 圆形碰撞 | `game/Collision.h` | 头文件(内联) | 相交/不相交/相切边界 |
| 常量与配置 | `game/GameConfig.h`、`game/waves/WaveDef.h` | 头文件 | 合理性断言（子弹快于敌机、池容量等） |

**渲染、音频、实体绘制、World 编排这些依赖 SFML 的部分不进单测**——它们通过
「本机 Ctrl+F5 运行 + 肉眼验证」来保障。这恰好印证了架构价值：
**因为 Game 层不依赖 SFML，纯逻辑才能被轻松隔离测试。**

### 1.3 怎么跑

```bash
# 配置（默认 BUILD_TESTS=ON，会生成 PlaneWarTests 目标）
cmake -B build
cmake --build build --target PlaneWarTests

# 运行（无需 SFML，纯控制台）
./build/PlaneWarTests        # 或 Windows 下 build/PlaneWarTests.exe
```

成功输出示例：
```
==== PlaneWar 单元测试 (21 cases) ====
[RUN] Vec2_Arithmetic
  -> ok
...
==== 21/21 通过，失败 0 ====
```

### 1.4 怎么加一个新测试

1. 在 `tests/` 新建 `test_xxx.cpp`；
2. `#include "test_framework.h"` 和你被测的头文件；
3. 写 `TEST(YourName) { EXPECT_*(...); }`；
4. 重新构建 `PlaneWarTests`（CMake `GLOB` 会自动纳入新文件）。

## 2. 内存安全：AddressSanitizer 零泄漏

### 2.1 先说结论：代码本身已「零泄漏 by construction」

全仓库 `grep` 过 `new / delete / malloc / free`——**结果为 0 处手动堆分配**。
所有动态资源都走两条安全路径：

- **资源缓存**（`AssetManager` / `AudioManager`）：`std::unique_ptr<sf::Texture>` 等，离开作用域自动释放；
- **高频实体**（子弹/敌机/敌弹/道具/粒子）：`ObjectPool<T>` 用 `std::vector<T>` **值存储**一次性预分配，运行期零分配、零释放；
- **其余对象**（Player / Boss / World）都是栈上或成员对象，随 World 析构而析构。

也就是说，「有没有泄漏」在架构层面就已经被锁死了——ASan 在这里的作用是
**把这件事变成可执行的证明，并捕获未来的回归**。

### 2.2 怎么开 ASan

CMake 提供了 `ENABLE_ASAN` 开关：

```bash
# GCC / Clang
cmake -B build -DENABLE_ASAN=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/PlaneWar

# MSVC（Visual Studio 打开文件夹时，在 CMake 设置里加变量 ENABLE_ASAN=ON，
#       并把配置切到 Release / RelWithDebInfo 再构建）
```

开关对各编译器的处理：

| 编译器 | 编译/链接 flag |
|---|---|
| GCC / Clang | `-fsanitize=address -fno-omit-frame-pointer` |
| MSVC | `/fsanitize=address`（配合 `/RTC-`、`/INCREMENTAL:NO`、`_ITERATOR_DEBUG_LEVEL=0`） |

### 2.3 MSVC 的一个重要坑（务必看）

MSVC 的 AddressSanitizer **与 Debug 配置的若干特性冲突**：

- `/ZI`（Edit-and-Continue 的调试信息格式）—— ASan 不支持；
- `/RTC`（运行时检查）—— 与 ASan 冲突；
- Debug 迭代器调试级别（`_ITERATOR_DEBUG_LEVEL=2`）—— ASan 下会误报。

因此 CMake 在 `ENABLE_ASAN=ON` 时已自动关掉 `/RTC`，并把迭代器调试级别降到 0；
**你仍需把构建配置选成 Release / RelWithDebInfo**（不要选 Debug）来避开 `/ZI`。
这也是为什么上面的命令显式写了 `-DCMAKE_BUILD_TYPE=Release`。

### 2.4 ASan 能抓到什么

- **堆越界 / 栈越界**（heap-buffer-overflow、stack-buffer-overflow）；
- **use-after-free / use-after-scope**；
- **泄漏**（GCC/Clang 的 LeakSanitizer 在进程退出时报告；MSVC ASan 同样会报告堆泄漏）。

本项目由于没有任何手动堆分配，理论上应得到「干净退出、零报告」。一旦将来有人
手滑写了 `new` 又忘了 `delete`，ASan 会在 CI 或本地第一时间亮红灯。
