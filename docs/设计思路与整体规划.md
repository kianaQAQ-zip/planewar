# 飞机大战 C++ 项目 · 设计思路与整体规划

> **用途**：面试 demo，向中小 / 独立游戏工作室展示 **C++ 基础 + 代码结构 + 设计模式**
> **技术栈**：C++17 + SFML 2.6（SDL2 作为备选）
> **范围**：纵向卷轴 + 玩家飞机 + 敌机 + 子弹 + 碰撞 + 波次系统 + Boss + 道具 + 分数 HUD
> **展示重点**：代码结构与设计模式（本文第 3 节是面试话术的核心）

---

## 0. 为什么是「纯 C++ + SFML」而不是 Unreal

你只有 Java/Python 底子、目标是展示**基础**，这个选择是经过权衡的：

| 方案 | 面试官实际看到的 | 结论 |
|---|---|---|
| 纯 C++ + SFML | 你自己写的游戏循环、实体管理、碰撞、对象池、设计模式 | ✅ 最能体现功底 |
| Unreal Engine 5 | 大量引擎样板，你的逻辑被 `UCLASS`/`UFUNCTION` 包裹 | ❌ 入门 demo 显得空 |
| 自研迷你引擎 | 最硬核但工期长，面试前做不完风险高 | ⚠️ 炫技过度 |

中小/独立工作室最关心的是：**你能不能把东西做出来、代码干不干净、会不会学**。一个 1500 行左右、架构清晰、用对了三四个经典模式的 SFML 项目，比一个撑不起来的 UE5 半成品强得多。

**SFML 选它的理由**：2D API 干净，自带窗口/输入/渲染/音频，你只需 `apt install` 或下预编译包就能跑，精力全放在「自己写的游戏逻辑」上，而不是和引擎搏斗。

## 0.5 图形与 HUD 资源方案（已定：Kenney 免费素材）

- **结论**：从 **M1 起**直接用 [Kenney 飞机大战素材包](https://kenney.nl/assets)（CC0 协议——可商用、可改、无需署名）。**不做图元（方块/圆）起步阶段**，省一道「换皮」里程碑，画面从一开始就接近真游戏。
- **加载链路**：`AssetManager`（单例）在启动时 `sf::Texture::loadFromFile("assets/player.png")` 缓存全部纹理；**实体不持有任何 SFML 对象**，只持有一个 `SpriteId`，由 `Renderer` 在 `Draw` 时查表取出 `sf::Sprite` 绘制。
- **SpriteId 锁定：`enum class`**（不用 string）。理由：编译期就能抓出「拼错精灵名」的 bug、零运行时字符串哈希开销；代价是新增种类要改枚举 + 维护映射表——MVP 阶段种类有限，这个代价可忽略。映射集中放在 `AssetManager` 里的一张 `std::unordered_map<SpriteId, const sf::Texture*>`。
- **HUD**：分数 / 血量 / 波次用 `sf::Font` + `sf::Text` 绘制（字体同样走 `AssetManager` 缓存，不重复加载）。
- **为什么这仍然证明架构**：哪怕一开始就是真贴图，「方块 ↔ 贴图」的切换依旧是 **Core 层一行改动**——因为 Game 层从没见过 `sf::Texture`。万一某张精灵图漏放，Core 里给个彩色矩形兜底即可，**Game 层零改动**。面试讲「渲染抽象 / 关注点分离」时，这就是现成证据。

## 1. 架构分层

把代码切成三层，层与层之间只向下依赖。这一刀本身就是面试加分项——说明你有「关注点分离」的意识。

```
┌─────────────────────────────────────────────┐
│  App 层   main.cpp / Game  (启动 + 主循环)     │  只负责"跑起来"
├─────────────────────────────────────────────┤
│  Game 层  Player / Enemy / Bullet / Boss /    │  纯玩法，不碰 SFML 窗口
│           WaveManager / ScoreManager /        │  （渲染细节下沉到 Core）
│           CollisionSystem / EventBus          │
├─────────────────────────────────────────────┤
│  Core 层  Window/Input/Renderer 封装、         │  对 SFML 的薄封装 +
│           ObjectPool<T>、Math(向量/AABB)、      │  可复用工具
│           AssetManager、Time/FixedStep       │
└─────────────────────────────────────────────┘
```

**关键纪律**：Game 层不要直接 `#include <SFML/...>`。所有 SFML 调用只在 Core 层。这样——以后你想换渲染后端（或加测试），只动 Core。面试官问「你怎么做解耦」，这就是活例子。

## 3. 设计模式清单（面试重点，逐条要能讲）

这是你文档和面试的「主菜」。每个模式我都标了**为什么用、用在哪、怎么讲**。

### 3.1 对象池 Object Pool —— 性能 + 内存的硬通货
子弹、敌机、粒子每秒可能生成/销毁几十个。如果每颗子弹都 `new`/`delete`，堆碎片 + 分配开销会拖垮帧率，还会引入悬空指针风险。
**做法**：`ObjectPool<Bullet>` 预分配 N 个，用完 `Release()` 回池而非 `delete`。
**面试讲法**：「热路径零分配（zero-allocation hot path），避免 GC 抖动那种问题，因为我根本没有 GC——C++ 里频繁 new/delete 是我自己要负的责。」

```cpp
template<typename T>
class ObjectPool {
    std::vector<std::unique_ptr<T>> pool;   // 拥有对象
    std::vector<T*> freeList;               // 可回收槽位
public:
    T* Acquire();        // 从 freeList 取，没有就 new
    void Release(T* p);  // 放回 freeList，不 delete
};
```

### 3.2 工厂 Factory —— 隐藏创建细节
`BulletFactory::Create(Player*, WeaponType)` 决定子弹速度/伤害/贴图。Enemy 同理。
**面试讲法**：「把『造什么』和『怎么用』分开。以后加一种敌机，只改工厂，调用方无感。」

### 3.3 状态模式 State —— 游戏流程 & Boss 阶段
- 游戏级：`MenuState / PlayingState / PausedState / GameOverState`，由 `Game` 持有一个 `IState*`。
- Boss 级：`BossPhase1 / BossPhase2 / BossEnrage`，Boss 自己切换。
**面试讲法**：「用状态机替代一堆 `if (state == ...)`，新增状态不用改旧逻辑，符合开闭原则。」

### 3.4 观察者 / 事件总线 EventBus —— 解耦
碰撞系统检测到「子弹击中敌机」不直接扣血、不加分的写死逻辑，而是 `bus.Emit<EnemyHitEvent>(enemy, dmg)`。ScoreManager、音效、粒子各自订阅。
**面试讲法**：「碰撞系统和计分系统互不认识，靠事件解耦。这是 ECS/Unity 事件系统的迷你版，说明我懂『低耦合』不是嘴上说说。」

### 3.5 策略 Strategy —— 敌机 AI 行为
`IEnemyBehavior` 接口，`StraightBehavior / SineBehavior / ChaseBehavior` 三个实现，Enemy 持有 `unique_ptr<IEnemyBehavior>`。WaveManager 按配置挑行为。
**面试讲法**：「同一种敌机换个行为就是新打法，运行时可切换，不必写 `if (type==...) else if (...)`。」

### 3.6 单例 / 服务定位（谨慎用）
`AssetManager` 用单例缓存纹理无可厚非，但**别到处用单例**。面试时要主动说：「单例方便但有隐藏全局状态、难测试的代价，所以我只在 AssetManager、Input 这种真正进程唯一的东西上用，系统编排都走显式依赖注入（构造传参）。」
> ⚠️ 主动暴露这个取舍，比「我全用单例」专业十倍。

## 4. 核心系统设计

### 4.1 实体模型（轻量组合，不过度设计）
入门项目**不要硬上完整 ECS**（那是 UE/Unity 量级的东西）。用一条干净的继承链 + 一个 `Update(dt)` / `Draw(renderer)` 接口就够：

```cpp
class Entity {
public:
    Vec2 position; Vec2 velocity; bool alive = true;
    virtual void Update(float dt) = 0;
    virtual void Draw(Renderer& r) = 0;
    virtual ~Entity() = default;   // 基类析构必须 virtual！
};
```

### 4.2 碰撞系统
- 子弹 vs 敌机 / 玩家 vs 敌机：圆形碰撞足够（距离 < r1+r2）。
- 玩家 vs 道具：AABB。
- 用空间网格（Grid Spatial Hash）优化：敌机多时别 O(n²) 两两比，把屏幕切成格子，只比同格/邻格。这是面试「性能意识」的杀手锏。

### 4.3 波次系统（数据驱动）
波次用一张配置表。MVP 阶段锁定用 **C++ 结构体数组**（`std::vector<WaveDef>`，编译期安全、零解析依赖、IDE 直接跳转）；**JSON 等外部数据驱动留到 M3 之后**——只有当你真需要「不重新编译就能改关卡」时才引入，那时再写个 `LoadWaves(path)` 解析即可，`WaveManager` 接口不变。每波定义：敌机类型、数量、生成间隔、行为、出现位置。
**好处**：加关卡不碰代码，设计师（或你）只改数据。面试讲「数据驱动 vs 硬编码」。

### 4.4 分数 / HUD
`ScoreManager` 订阅 `EnemyKilledEvent` 加分，`Hud` 每帧从它读数值画文字。血量同理来自 Player 的状态。

## 5. 游戏循环（固定时间步）—— 专业度的分水岭

**永远用固定步长更新 + 可变渲染**，不要「每帧按真实 dt 直接更新物理」。

```cpp
const float STEP = 1.0f / 60.0f;   // 固定 60Hz 逻辑
float accumulator = 0.0f;
while (window.isOpen()) {
    float frame = clock.restart().asSeconds();
    accumulator += frame;
    while (accumulator >= STEP) {      // 逻辑按固定步长跑
        Update(STEP);                  // 确定性、稳定、可回放
        accumulator -= STEP;
    }
    Render(accumulator / STEP);        // 渲染用插值因子，画面平滑
}
```

**面试讲法**：「固定步长让物理/碰撞和帧率解耦——低端机掉到 30fps 时，游戏速度不变，只是渲染少画几帧。这是专业游戏循环和『新手每帧直接乘 dt』的本质区别。」

## 6. 内存与性能策略（C++ 面试高频区）

- **拥有权清晰**：对象池用 `unique_ptr` 拥有；系统间传引用用原始指针/引用（不拥有）；跨模块缓存用 `weak_ptr` 防悬空。
- **绝不每帧 `new`**：子弹/敌机全走对象池。
- **无泄漏验证**：编译加 `-fsanitize=address`（GCC/Clang）或 Visual Studio 的 `/fsanitize=address`，跑一遍看有没有泄漏报告。面试可以说「我用 ASan 验证过零泄漏」。
- **避免无谓拷贝**：传参用 `const T&`，返回大对象考虑移动语义。
- **热路径不分配**：`Update`/`Draw` 里不创建 `std::vector`、不 `new`。

## 8.5 M3 实现说明（Boss / 道具 / 音效 / 粒子）

M3 在保持「三层架构 + Game 层零 SFML 引用」纪律的前提下，补上了四个子系统。核心取舍都围绕**解耦**与**优雅降级**：

### 8.5.1 Boss —— 状态机（State）
- `Boss` 用显式枚举 `EBossState{ Entering, Phase1, Phase2, Defeated }` + 每状态更新分支，替代 `if (state==...) 地狱`。
- 进场 → 常规弹幕 → （血量过半）狂暴弹幕 → 被击毁。新增阶段只需加枚举值 + 一段 `case`，符合开闭原则。
- **发射解耦**：Boss 不知道子弹池长什么样，只对 `EventBus` 发 `BossFireEvent{原点, 弹幕模式, 玩家位置}`，由 `World` 订阅并生成敌弹。这样 Boss 与子弹系统互不认识——事件总线价值的又一实证。
- 弹幕两种模式：五路扇形（Phase1）、八路环形（Phase2）。

### 8.5.2 道具 —— 策略（Strategy）
- `IItemEffect` 接口 + 三个无状态实现：`HealEffect`（回血）/ `RapidFireEffect`（升武器等级）/ `ShieldEffect`（护盾）。
- `PowerUp` 池化实体只持有「非拥有的常量指针」指向静态效果实例——既用上策略模式，又保证对象池要求的「实体可拷贝」（`unique_ptr` 会导致不可拷贝，这里刻意避开）。
- 拾取时 `it.ApplyTo(player_)` 把效果委托给策略对象，容器无需写 `if (kind==...) else if (...)` 分支。

### 8.5.3 音频 —— AudioManager（单例，Core 层）
- 与 `AssetManager` 同理：进程唯一的引擎服务才用单例。`Play(name)` 在资源缺失时**静默返回**，游戏照常运行；需要 `openal32.dll`（CMake 构建后自动拷贝）。
- 触发点集中在 `World` 的碰撞/生成逻辑里（击杀、命中、拾取、Boss 进场/死），不放进 Game 实体，避免 Game 层反向依赖 Core 音频。

### 8.5.4 粒子 —— 对象池 + 渲染抽象
- `Particle` 走 `ObjectPool<Particle>`，爆炸瞬间批量 `Acquire`，生命耗尽自动回收（热路径零分配）。
- 淡出用「缩小 + 降 Alpha」实现，不引入额外纹理；Alpha 合成时注意 SFML 颜色是 `0xRRGGBBAA` 字节序。
- `Renderer` 新增 `DrawCircle`/`DrawRect` 两个原语，供粒子与 Boss 血条使用——依旧把 SFML 关在 Core 里。

### 8.5.5 玩家增强（配合道具）
- `Player` 内聚武器等级（多发散射）、护盾、受击短无敌三种状态；由道具策略通过 `AddLife / UpgradeWeapon / AddShield` 间接修改，互不耦合。
- 受击后 `PLAYER_HIT_INVULN` 秒无敌，避免一帧被多颗子弹/碰撞重复扣命（健壮性细节，面试可讲）。

---

提前背熟这几句，面试官一问「你这个项目用了什么设计模式」，你就能逐条甩出来（详见第 3 节）。重点不是"用了多少"，而是**每个都为解决具体问题而用，且你知道代价**：
- 对象池 → 热路径零分配、避悬空指针
- 状态机 → 替代 if 地狱、开闭原则
- 事件总线 → 系统解耦、低耦合实证
- 策略 → 运行时换行为、免分支
- 单例克制 → 主动暴露取舍，显专业

## 10. 明确不做的事（控制范围 = 控制风险）

- ❌ 不做网络游戏（要 replication，工期爆炸）
- ❌ 不做 3D / 不做关卡编辑器
- ❌ 不引入完整 ECS 框架（over-engineering）
- ❌ 不堆特效到看不清玩法

**范围克制本身就是成熟工程师的标志。** 一个干净、能跑、模式清晰的小项目，远胜一个半成品大饼。
